# Правила работы агентов в проекте

Действуют для всей папки проекта. Обновлено: 20 октября 2026.
Цель: сокращать суммарные затраты на принятую задачу, сохраняя качество,
скорость выполнения и производительность создаваемого продукта.
Это рабочая политика, а не гарантия экономии: эффект подтверждается измерениями.
Прямые указания пользователя и системные ограничения имеют приоритет.

## Локальная разработка и GitHub

- Для изменений интерфейса соблюдать `docs/brandbook.html`: палитру, типографику,
  объёмные карточки и кнопки, короткие подписи и честные состояния поиска.
  Согласованные изменения концепции сначала отражать в брендбуке, затем в экранах.

- Всю разработку, сборку, тестирование и проверки выполнять локально.
- GitHub использовать для выгрузки исходников и истории проекта.
- Не настраивать и не запускать GitHub Actions, облачные тесты, Codespaces
  или удалённую разработку без прямого изменения этого требования пользователем.
- Перед выгрузкой выполнить относящиеся к изменениям локальные проверки.
- Не выгружать секреты, локальные настройки доступа, скачанные инструменты,
  зависимости и временные результаты сборки.

## Выбор исполнителя

Главный агент отвечает за требования, выбор исполнителя, интеграцию и итог.
Маленькую задачу выполняет сам: передача другому агенту тоже стоит времени и токенов.
Для существенных независимых подзадач эта инструкция предписывает делегирование
по таблице ниже, когда ожидаемая польза превышает расходы на передачу и проверку.
Не запускать все модели ради самого распределения ролей.

| Модель | Роль в проекте | Начальный reasoning_effort |
| --- | --- | --- |
| `gpt-6.1-sol` | Основной разработчик и координатор: реализация функций, интеграция, отладка, проверка изменений | `medium`; `high` для сложных дефектов |
| `gpt-6-luna` | Узкий помощник: поиск по заданной области, извлечение фактов из логов, небольшие механические правки по точному образцу | `low` для механики, `medium` для анализа |
| `gpt-6-astra` | Эксперт по трудным решениям: архитектурные противоречия, распределённые алгоритмы, сложные гонки, критичный анализ безопасности | `low`; `high` при нерешённой сложности |
| `gpt-6-sol` | Резерв основного разработчика, если 6.1 Sol недоступна или измерения на проекте оправдывают замену | `medium` |
| `gpt-5.6-sol` | Резерв совместимости для существующих задач при недоступности основных исполнителей | `medium` |

Это назначение ролей проекта. Оно не утверждает, что резервные модели дешевле.
Перед вызовом проверить фактический список моделей и допустимых уровней инструмента.
Модели, видимые только в селекторе новых чатов, не считать доступными субагентам.
Новые модели не включать автоматически без проверки пригодности.
При недоступности нужной модели выбрать доступный резерв и сообщить о замене.

Главная модель текущего чата не переключается от записи в этом файле.
Маршрутизация применяется к запускаемым субагентам; не создавать новые чаты
и не менять глобальную конфигурацию ради обхода ограничений.

## Делегирование

- По умолчанию достаточно главного агента; для объёмной изолированной работы — одного помощника.
- Параллельно выполнять независимые работы, если это сокращает время до результата.
  В текущей среде максимум четыре агента вместе с главным; актуальный лимит инструмента приоритетнее.
- Каждый файл в один момент имеет одного ответственного редактора.
  Проверяющий читает результат после завершения соответствующих изменений.
- Субагентам запрещено порождать следующих агентов без решения координатора.
- При `spawn_agent` явно задавать `model`, `reasoning_effort`, `fork_turns: "none"`.
  Передавать ограничения проекта и нужные выдержки: чистый контекст не содержит историю чата.
- Исправления возвращать существующему исполнителю через `followup_task`.
  Не нанимать нового агента для каждого небольшого замечания.

Задание помощнику должно содержать: цель; входные файлы; разрешённые изменения;
ограничения; критерии готовности; команды проверки, если они известны.
Ответ: статус; результат; файлы и строки; проведённые проверки; оставшиеся риски.
Обычный отчёт — до 250 слов, с расширением только для существенных доказательств.
Ограничение области работы является инструкцией, а не технической изоляцией доступа.

## Уровень сложности и эскалация

1. Однозначная локальная задача: выполнить напрямую или передать Luna,
   только если объём работы оправдывает отдельный запуск.
2. Новое поведение, несколько связанных файлов, неизвестная причина дефекта:
   сразу Sol; не тратить попытки слабой модели на заведомо сложную работу.
3. Если Luna не решила задачу после одной содержательной попытки исправления,
   передать Sol факты, симптомы и уже проверенные гипотезы.
4. Если Sol упёрлась в архитектурную неопределённость или две неудачные гипотезы,
   привлечь Astra для конкретного вопроса. Ошибки сети или окружения сначала
   диагностировать инструментами: более сильная модель не заменяет доступ.
5. Уровни `xhigh`, `max`, `ultra` включать только при конкретной необходимости,
   объясняя ожидаемую пользу. Не делать их настройкой по умолчанию.

Если проект действительно реализует распределённую сеть, изменения консенсуса,
репликации, обработки разделения сети, ключей и аутентификации считать критичными.
Для них нужна независимая проверка Sol (`high`) либо Astra и проверяемые сценарии отказов.
Luna не принимает такие решения и не выполняет единоличную итоговую проверку.

## Экономия контекста

- Сначала `rg --files` и адресный поиск, затем нужные фрагменты файлов.
  Не читать весь репозиторий, большие логи и зависимости без причины.
- Независимые чтения объединять в вызов; решения, записи и зависимые шаги выполнять последовательно.
- Использовать команды и скрипты для механической обработки данных.
  Не передавать модели тысячи строк, если инструмент может вернуть нужные совпадения.
- Не повторять поиск, проверку или анализ, пока входные данные не изменились.
- Передавать пути, интерфейсы и выводы вместо полного диалога и копий файлов.
- Не создавать отдельного агента только для пересказа готового ответа.
- Сохранять существенные решения рядом с кодом; при длинной работе вести короткую
  запись текущего состояния с принятыми решениями и следующим шагом.
- Не загружать вспомогательные материалы и навыки без отношения к текущей задаче.

## Приёмка и контроль результата

Перед изменением определить проверяемый критерий готовности. После изменения
выполнить относящиеся к нему проверки и обязательные проверки репозитория.
Не заменять проверку уверенным текстом субагента.
Для исправления ошибки по возможности подтвердить воспроизведение и регрессионный сценарий.
Для простой правки документации достаточно проверки содержания и сохранённого файла.
Повторные полные тесты нужны при новых изменениях или новых основаниях сомневаться.

При изменении горячего пути сравнивать время, пропускную способность и ресурсы
с исходным вариантом в одинаковых условиях. Не жертвовать корректностью ради токенов.
Успешные тесты сами по себе не доказывают отсутствие ухудшения производительности.

На первых десяти содержательных задачах оценить подход по типам работ:
время до принятого результата, число доработок, успешность проверок и суммарные токены
всех агентов, если среда предоставляет эти данные. Отсутствующие показатели помечать
«нет данных»; не подменять их лимитом аккаунта или выдуманной оценкой.
Для вывода об экономии сравнивать с сопоставимым одноагентным выполнением.
Не запускать платные дубли задач только ради статистики без запроса пользователя.
Токены, денежная стоимость и скорость — разные показатели.
Если делегирование регулярно замедляет работу или ухудшает приёмку, упростить маршрут.

Завершать ответом: что сделано, что проверено, какое существенное ограничение осталось.
Не вводить дополнительные согласования для обычных уже разрешённых действий.
