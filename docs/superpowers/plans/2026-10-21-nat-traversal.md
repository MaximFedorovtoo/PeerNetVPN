# Проверка и внедрение прямого обхода NAT

Требование: телефоны в мобильной и Wi-Fi-сетях соединяются без USB как
транспорта, выделенного сервера проекта и изменения настроек роутеров.

## Критерий готовности

Реальный двусторонний канал через разные физические сети; затем VPN для
выбранного приложения с выходным адресом другого телефона, а исключённое
приложение сохраняет адрес своей сети. USB не передаёт VPN-пакеты или
приглашения в итоговом сценарии. Отдельная диагностика через ADB не является
доказательством готовности этого сценария.

## Порядок

1. С того же UDP-сокета на каждом телефоне запросить публичные STUN Google
   и Cloudflare. Проверять источник, transaction ID и формат ответа.
2. Проверить одновременный обмен ограниченными аутентифицированными
   диагностическими пакетами по полученным адресам. Сохранить счётчики и
   ограничения вывода: неудача не доказывает невозможность всех NAT-методов.
3. При работоспособном прямом пути внедрить готовый надёжный ICE/DataChannel
   транспорт, сохранив проверку ключей и правила общего доступа ядра.
4. Для начального сопряжения без собственного signaling-сервера использовать
   обмен короткоживущими приглашениями пользователем. STUN не является
   каталогом и не переносит приглашения. Выбор уточняется у пользователя.
5. Независимая проверка критического транспорта; локальные тесты отказов,
   лимитов, закрытия и повторного подключения; сборка Android.
6. Проверка на устройствах без USB-моста и без ADB-обмена приглашениями.

## Ограничения

Публичный STUN — внешняя зависимость. Некоторые комбинации отображения и
фильтрации NAT требуют ретранслятора. Нельзя сообщать об успешном обходе
только по ответу STUN или по локальному тесту. Другой VPN пользователя на
мобильном устройстве не отключается; диагностический сокет привязывается к
физической сети Android.

Сборки и тесты выполняются локально. Показатели суммарных токенов агентов:
нет данных.
