# Измерение исходящей скорости

Проверено 21 октября 2026. Измерение использует `PhysicalNetwork.http()` выбранной физической Android-сети, HTTPS с обычной проверкой цепочки сертификата и имени сервера. Cloudflare не используется. Проверка не останавливает VPN; жизненным циклом приложения управляет контроллер.

## Ресурсы и контракт

| Назначение | Публичный upload URL | Основание |
| --- | --- | --- |
| Основной | `https://speedtest.selectel.ru/empty.php` | [Официальный Selectel Speedtest](https://selectel.ru/speedtest/); его [frontend-модуль](https://cdn.selectel.ru/site_v3/_nuxt_v3/DbP68OEs.js) явно задаёт `url_ul` с этим адресом, а [worker](https://selectel.ru/speedtest/speedtest_worker.min.js) выполняет POST с `Content-Encoding: identity`. |
| Резервный | `https://speedtest.59telecom.ru/backend/empty` | [Официальный 59telecom LibreSpeed](https://speedtest.59telecom.ru/) подключает [список серверов](https://speedtest.59telecom.ru/servers_list.js), где `ulURL` равен `backend/empty`. |

Это штатные обработчики загрузки LibreSpeed, а не произвольные URL для отправки POST. [Официальный PHP backend](https://github.com/librespeed/speedtest/blob/master/backend/empty.php) отвечает HTTP200 с пустым телом, `Cache-Control: no-store, no-cache, ...`. [Документация LibreSpeed](https://github.com/librespeed/speedtest/blob/master/doc.md) определяет `ulURL` как адрес теста загрузки. У 59telecom путь без расширения PHP, опубликованный самим оператором; ответы проверены отдельно.

Успех требует всех трёх признаков: HTTP200, директивы `no-store` и `no-cache`, и полностью пустое тело. Объединяются все значения Cache-Control: оба ресурса присылают несколько строк этого заголовка, последняя может содержать только `post-check=0, pre-check=0`. Редиректы, HTML-заглушки с HTTP200, сообщения об ошибке PHP и другие непустые ответы отклоняются. Сервер не возвращает квитанцию с числом принятых байтов: используется контракт завершённого фиксированного POST, а не доказательство максимальной скорости канала.

## Объём, время и расчёт

Калибровка сначала отправляет 256 КиБ прогрева каждому используемому провайдеру. Прогрев не входит в итоговую скорость: его подтверждённая скорость определяет размер основной пробы, рассчитанной примерно на 3 секунды передачи. Затем выполняются до двух последовательных основных проб от 256 КиБ до 16 МиБ; второй размер адаптируется по первой. Общий предел — 24 МиБ upload payload за вызов, включая прогрев и неудачные попытки. Весь размер запроса резервируется до открытия соединения, поэтому частичные ошибки не позволяют превысить бюджет. Заголовки HTTP/TLS, TCP подтверждения и транспортные повторы в этот предел не входят.

Подключение и чтение ограничены 8 секундами; отдельная попытка — 20 секундами, вся калибровка — 45 секундами. Сторож проверяет отмену и сроки каждые 100 мс и вызывает `disconnect()`, в том числе при заблокированной записи. Фактическое завершение сетевого вызова зависит от сетевого стека Android. При отмене новые попытки не начинаются. После ошибки разрешён только переход к опубликованному резервному endpoint; перенаправления запрещены.

Таймер скорости начинается после получения выходного потока HTTPS, перед первой записью тела; DNS, TCP и TLS установка исключаются. Он заканчивается только после завершения POST и проверки полного ответа сервера. Поэтому быстрая запись в локальный сокетный буфер сама по себе не считается скоростью канала. Расчёт — `payloadBytes / elapsedSeconds` в байтах/с, минимум успешных основных проб. Скрытый коэффициент 0.8 удалён: лимит раздачи уже составляет треть измеренного значения. Прогрев не используется как запасной результат, если ни одна основная проба не завершилась успешно.

Это оценка исходящей одиночной HTTPS-передачи до выбранного сервера, а не многопоточный speedtest: маршрут, загрузка сервера, RTT, TCP slow start и предел 24 МиБ могут давать отличия от специализированного теста, особенно на очень быстрых каналах. Пустой ответ обработчика подтверждает завершённый HTTP-запрос по контракту провайдера, но не содержит независимой квитанции числа байтов. Измеряется upload, не download. Служебный трафик не начисляется в `sharedBytes`/`receivedBytes` узла. При автоматическом повторе каждые 15 минут теоретический максимум полезной нагрузки — 96 МиБ/час непрерывной работы, без ручных повторов.

## Воспроизводимая проверка

`tools/test-speed-endpoints.ps1` отправляет по 64 КиБ случайных данных двум фиксированным upload URL, сохраняет заголовки и результаты в `.tools/speed-probes/`. Можно задать `-AdbSerial b95aef09` для native curl на подключённом Android; этот режим использует штатный маршрут shell и сам по себе не доказывает привязку к физической сети. Скрипт не отключает VPN и не ослабляет TLS.

Локальные пробы через native curl мобильного устройства 21.10.2026:

| Endpoint | Upload payload | HTTP | Тело | Директивы кеша | Время |
| --- | ---: | ---: | ---: | --- | ---: |
| Selectel | 65536 байт | 200 | 0 байт | no-store, no-cache | 0.387 с |
| 59telecom | 65536 байт | 200 | 0 байт | no-store, no-cache | 0.390 с |

Повторная проверка воспроизводимым скриптом на WiFi-телефоне также прошла для обоих ресурсов: Selectel — 0.166 с, 59telecom — 0.267 с, по 65536 байт, HTTP200 и пустое тело. Сырые результаты находятся в локальной `.tools/speed-probes/`; они не включаются в исходники.

Сертификаты проверялись штатно, без `-k`. На телефоне оставался сторонний `tun0`; результаты shell подтверждают контракт с этого устройства, но не отдельную физическую маршрутизацию. Desktop-соединение в то же время получало таймауты; это дополнительное основание не обещать доступность ресурса во всей России.

Android instrumentation `org.uzel.app.InternetMeasurementTest#testUploadOverExistingPhysicalNetwork` проверяет уже сам API приложения: выбирает существующую сеть с `INTERNET` и `NOT_VPN`, вызывает текущий upload с лимитом 24 МиБ и сообщает байты/с и тип физического транспорта. Оно не создаёт VPN и не меняет состояние сетей. Успех необходимо проверять на фактическом устройстве и операторе; общероссийская доступность из этих проверок не следует.

Исторические результаты прежнего алгоритма (2 × 1 МиБ и коэффициент 0.8; не результаты обновлённой калибровки): эта instrumentation-проверка после исправления обработки повторных Cache-Control успешно выполнена локально 21.10.2026 на двух подключённых телефонах:

| Физический транспорт из результата теста | Результат калибровки | Максимум payload за вызов | Статус |
| --- | ---: | ---: | --- |
| cellular | 832742 байт/с | 3145728 байт | PASSED |
| wifi | 3463450 байт/с | 3145728 байт | PASSED |

Это уже консервативные значения, возвращённые приложением: учтено время установки соединения и получения ответа, применён коэффициент 0.8. Они не являются измерением тарифной или максимальной скорости, и различие между телефонами не является сравнением их операторов в одинаковых условиях. Тесты выполнялись с существующими сетями; сторонний VPN не отключался.

Обновлённая калибровка выполнена на реальных физических сетях при запуске VPN-тестов 21.10.2026: мобильная сеть — 1 708 521 байт/с (13,7 Мбит/с), Wi-Fi — 41 632 137 байт/с (333,1 Мбит/с). Следующий запуск дал соответственно около 9,6 и 274,0 Мбит/с: это отдельные измерения, а не гарантированная скорость тарифа. Общий предел раздачи рассчитывается как треть результата в байтах/с; интерфейс переводит его в Мбит/с через ×8 / 1 000 000. Сравнения с одновременно запущенным внешним многопоточным тестом не проводилось.

Проверки чистой Java-логики: 11 тестов `UploadMeasurementTest` покрывают контракт ответа, расчёт, исключение установки HTTPS и прогрева из оценки, включение полного ответа, fallback и учёт бюджета при ошибках, отключение кеша/редиректов и отмену. Все сборки и тесты выполняются локально; GitHub Actions не используются.
